# 性能基线与优化规范 (Performance Baseline & Benchmark)

## 一、性能作为一级目标 (Performance as a Tier-1 Citizen)

在浏览器扩展（特别是具有全文扫描和高亮标注特性的阅读扩展）开发中，“功能能跑通”绝不是合格标准。
原生 Safari 用户对于网页加载延迟、风扇狂转、打字掉帧、内存膨胀极为敏感。因此，Glint Safari Personal Edition 必须确立严格的量化性能指标 (SLAs)。

---

## 二、核心性能指标与 SLA 规范

| 性能指标项 | 测量方式 / 场景 | 原版 Chrome 表现 | Safari Personal 目标 SLA | 优化策略 / 根因治理 |
| :--- | :--- | :--- | :--- | :--- |
| **首屏加载影响 (FCP / LCP)** | Lighthouse / Web Vitals | 偶有微小延迟 | **零影响 (0ms 阻塞)** | Content Script 配置 `runAt: document_idle` + `requestIdleCallback` 启动，绝不与网页关键渲染路径抢占主线程 |
| **首屏全量扫描耗时** | 典型英文维基百科 (约 5000 词) | 18 ~ 32ms | **< 8ms** | 高效 TreeWalker 遍历、预编译分词正则、代码块延迟扫描 |
| **大型长篇文档扫描耗时** | 5 ~ 10 万词长篇学术论文/规范 | 70 ~ 150ms (偶发 Long Task) | **< 30ms** | 字符数早筛、短路分支优化、无 DOM 插入开销 |
| **MutationObserver 增量耗时** | 动态新增单个段落或评论 | 20 ~ 50ms (因全页全量重扫) | **< 2ms** | 废弃整页重扫，实施基于变动节点的局部子树增量扫描 |
| **流式打字机场景耗时** | 模拟 ChatGPT / Claude 连续高频输出 | 每 500ms 触发一次全页全量重扫 | **< 3ms 批处理，0 Long Task** | 合并连续 characterData 变动，只分析变动的单行文本节点 |
| **主线程 Long Task (> 50ms)** | 持续滚动、输入、动态交互 | 存在突发峰值 | **0 次 Long Task** | 所有密集型计算均分片或防抖，确保流畅 60fps |
| **标签页内存增量 (Per-tab RSS)** | 单标签页注入后内存增量 | ~15MB (大 Map 强引用) | **< 3MB** | 采用惰性解压数据结构、消除无效克隆 |
| **内存泄露 (Detached DOM Leak)**| 动态移除 1000 个高亮节点后 GC | 存在（强引用 Map 阻止回收） | **0 泄露 (WeakMap 自动 GC)** | 核心索引全面迁移为 `WeakMap<Text, Token[]>` |
| **空闲 CPU 占用率** | 页面静止阅读状态 | 0% | **0.0%** | 无任何定时器轮询，事件驱动架构 |

## 三、原版与 Safari-First 深度架构对比

```
[原始 Chrome 架构方案]
DOM 变动发生 ──> 500ms 防抖 ──> 全量递归遍历 document.body ──> 提取整页所有文本 ──> 全量正则分词 ──> 重新创建几千个 Range ──> 重新提交整页 Highlight
(后果：SPA 页面 CPU 持续飙升，长列表不断卡顿，强引用阻止旧节点 GC)

[Safari-First 高性能重构方案]
DOM 变动发生 ──> 脏节点微任务合并 (Batching) ──> 仅遍历发生变动的局部子树 ──> 仅增量计算新增/改变的 Token ──> 增量更新 Range 列表与 WeakMap
(效果：耗时由数十毫秒骤降至 1~2 毫秒，不产生可察觉的掉帧，旧节点自然 GC)
```

## 四、基准压测场景与验证方法

为了在后续开发阶段持续度量，设立以下四个固定 Benchmark 页面模型：

1. **基准 1：静态长文模型 (Wikipedia Article)**
   - 文本量：~8,000 词。
   - 检验指标：首次扫描执行耗时、Range 生成耗时、内存初始驻留。
2. **基准 2：高频流式输出模型 (Streaming Chatbot)**
   - 行为：每 50ms 向 DOM 追加 5~10 个单词（模拟大语言模型流式输出），持续 15 秒。
   - 检验指标：CPU 占用率、主线程 Long Task 数量、增量批处理耗时。
3. **基准 3：无限滚动长列表模型 (Infinite Feed)**
   - 行为：每次向下滚动追加 20 条图文卡片，反复滚动 50 次（累计 1000 个卡片）。
   - 检验指标：内存稳态增长曲线、DOM 节点是否滞留、滚动帧率 (FPS)。
4. **基准 4：极端巨型文档模型 (Mega Document)**
   - 文本量：100,000 词（整本技术规范）。
   - 检验指标：分词算法边界防御、MAX_TOKENS 保护阈值有效性。
